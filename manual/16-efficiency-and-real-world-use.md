# 16 · Efficiency: tokens, speed and demanding environments

**Who this is for:** developers who work with coding agents (Claude Code, Codex, Cursor or others) and teams that
bring this workflow into large projects, with many parallel sessions, long test suites and a watched budget.

**Rule:** cost is measured per useful outcome (a verified, landed change), not per token or per line. You save by
removing what adds nothing (useless context, long outputs, repeated reasoning, work a script does better), **never**
by relaxing final verification. A shortcut that lowers quality is not adopted (principle 10).

## 0. How to use this repo in real projects

This repo is **not copied wholesale into each project, and it is not loaded into the agents' context.** It is split
into three layers, each with its own context cost and its own way of reaching the project:

| Layer | What it is | How it reaches the project | Context cost per turn |
| --- | --- | --- | --- |
| **1. Plugin** | skills (`playbook`, `worktree`, `tdd`, `debug`, `verify`, `review`, `new-adr`, `land`, `audit-repo`, `adopt`), review agents, hooks | marketplace + `enabledPlugins` in the project's `.claude/settings.json` | only the names and descriptions of what the model can invoke (a few hundred tokens); bodies load on use |
| **2. Project files** | `CLAUDE.md`, `.claude/settings.json`, `scripts/dev/*`, architecture and docs tests, CI, ADRs | generated by `adopt` from `templates/`, following the reference implementation described in `reference/README.md` | only `CLAUDE.md` (< 200 lines) |
| **3. Manual** | chapters, anti-patterns, checklists | stays in this repo; the `playbook` skill reads **one** chapter when needed | zero unless consulted (1–6k tokens per chapter) |

**Never** paste manual chapters into `CLAUDE.md` or a system prompt: you would pay ~50k tokens on every turn for
rules the agent needs once a month. What always applies fits on one page (`skills/playbook/rules.md`) and arrives
through the skill.

Agents that are not Claude Code (Codex, Cursor, others) do not load plugins. Point them at `AGENTS.md`: it routes
each task to the one file it needs, and layer 2 (the project files) works the same for every agent.

### Install (once per developer)

The repo is both a marketplace (`agentic-coding-swarm-protocol`) and a plugin (`swarm`). Fork it or use it as
is, then, inside Claude Code:

```
/plugin marketplace add AntoniArco/agentic-coding-swarm-protocol
/plugin install swarm@agentic-coding-swarm-protocol
```

From a shell, the equivalent is:

```bash
claude plugin marketplace add AntoniArco/agentic-coding-swarm-protocol
claude plugin install swarm@agentic-coding-swarm-protocol
```

Check it: `/plugin` lists `swarm` as enabled, the skills appear as `/swarm:<skill>`,
and `/context` shows only their descriptions, not their bodies. The hooks do nothing in a repo that has not adopted
the protocol (no `swarm.json` at its root), so installing it globally is safe. What a project must expose (commands,
hooks, conformance checks per level, stack equivalents, agents without hooks) is defined once in
[INTEGRATION.md](../INTEGRATION.md).

### Make it the team default (once per project)

So that everyone who opens the project gets it, commit this to the project's `.claude/settings.json`:

```json
{
  "extraKnownMarketplaces": {
    "agentic-coding-swarm-protocol": {
      "source": { "source": "github", "repo": "AntoniArco/agentic-coding-swarm-protocol" }
    }
  },
  "enabledPlugins": { "swarm@agentic-coding-swarm-protocol": true }
}
```

Claude Code offers to install it to anyone who trusts the project folder. To enforce it across a company, use
managed settings with the marketplace allowed and the plugin forced on. Pin versions: the plugin carries a
`version` in `.claude-plugin/plugin.json`, changes ship as releases, and projects pick them up when the marketplace
updates. One playbook owner reviews plugin changes like any other code.

### Adopt it in a project (agent-driven, one level per session)

In a session inside the target project:

```
/swarm:adopt 0 --plan   # detects stack and scenario, writes the adoption ADR, stops
/swarm:adopt 0          # CLAUDE.md, settings (secret deny rules), .gitignore, ADR
/swarm:adopt 1          # verify + mirrored CI + coverage floor
/swarm:adopt 2          # worktrees + land (or PR mode) + invariants + docs test
```

Rules for the rollout:

- **One level per session** (clean context), each with its own verification and its own commit. Run `/clear`
  between levels.
- **Read the `--plan` output before running level 0.** It names the scenario (table below) and what will not be
  adopted. If the scenario is wrong, say so before any file is written.
- **Templates are merged, never pasted.** The skill reads the existing `CLAUDE.md`, CI and settings first and never
  weakens what the project already enforces.
- **Level 3** (OpenSpec, audits, scheduled reviews) only after levels 0–2 have run for two weeks. Full detail per
  level: `ADOPTION.md`.

What a level-2 project has, at minimum: a `CLAUDE.md` under 200 lines, secret `deny` rules, `pnpm verify` (or your
stack's equivalent) with `--quick` and full modes identical to CI, one worktree per session, serialized integration
through `land` or a merge queue, an architecture test for the invariants, and a docs test that fails on stale
references.

| **B. Legacy repo with 30+ minute CI** | worktrees, `verify --quick`, reviews | full `verify` does **not** run inside local `land`: `land` rebases, runs quick and opens a PR; the merge queue runs the suite **sharded** (`--shard`) in CI. | **C. Monorepo with many packages** | everything | `verify --quick` per affected package; minimal root `CLAUDE.md` plus one per package (loaded when working inside it); `.claude/rules/` with `paths:` per package; architecture tests on inter-package dependencies |

### How an agent works in a project that already uses it

1. It starts in its own worktree (`claude -w <task>`). The session hook installs dependencies, assigns ports and
   prints only actionable warnings.
2. Its context holds the project's `CLAUDE.md`, the plugin's descriptions and nothing else from the playbook.
3. When unsure about the workflow, it invokes `/swarm:playbook <topic>`: that reads `rules.md` and,
   if needed, one chapter.
4. It iterates with `verify --quick`, finishes with full `verify`, and asks for `reviewer` (plus
   `security-reviewer` on sensitive paths).
5. It commits with `wt:commit` and `Assumption:` trailers, and integrates with `land` (or a PR in scenarios B and D).
6. The `Stop` hook leaves a `wip:` commit so nothing is lost; `gc` removes the worktree once it has landed.

### Rolling out across an organization

1. **Pilot** with one team and one repo for two weeks. Measure the baseline first (§10).
2. **A playbook owner** (one person) who reviews changes to the plugin and the templates.
3. **Expand** to more teams only if the metrics improve, or hold steady with less human intervention. Write the
   rollback criterion before you start.
4. **Feedback loop:** what one team learns (a new anti-pattern, a rule that adds nothing) comes back here as a PR to
   the playbook, with its incident.

### What breaks in real environments (and how to avoid it)

- **16 GB laptops:** 1–2 sessions verifying at once, not 4. Stop dev servers when you are done looking.
- **Windows:** use WSL2; the process scripts read `/proc` on Linux and `lsof` on macOS.
- **Corporate networks:** pin the package registry and the allowed URLs; the Claude Code sandbox honors
  `WebFetch(domain:...)` rules.
- **Repos with secrets in a development `.env`:** `deny` rules in settings from day one; no `.worktreeinclude` with
  keys.
- **Teams that already have a long `CLAUDE.md`:** do not replace it; trim it with `/doctor` and move procedures into
  skills.
- **A plugin with too many model-invocable skills:** every description costs tokens on every turn. Skills with side
  effects (`land`, `adopt`) set `disable-model-invocation: true`, which also takes them out of context.

## 1. Where the tokens go

Every turn resends the whole conversation. The real cost of a session is roughly:

```
cost ≈ Σ per turn ( accumulated context × (1 − cached fraction) + output + reasoning )
     + subagents (each with its own context)
     + compactions (reading the whole conversation to summarize it)
```

The levers, from most to least impact:

| Lever | Effect | How |
| --- | --- | --- |
| **Accumulated context** | multiplies every turn | one task per session; `/clear` between tasks; short outputs |
| **Cache hit rate** | cached tokens cost a fraction | stable prefix; do not leave a session idle longer than the cache TTL |
| **What enters context** | paid on every following turn | summary + tail instead of logs; `head`, filters, LSP; no whole files you will not edit |
| **Effort level and model** | reasoning and price per token | medium effort by default; high only where getting it right is hard; small model for simple subagents |
| **Subagents** | each pays for its own context | only to parallelize, isolate noise or review with fresh eyes |
| **Repetition** | corrections, retries, re-reads | specific prompt from the start; a check that returns pass/fail; `/clear` after two corrections |

## 2. Context: what loads, and when

### Loaded in every session (fixed cost)

- `CLAUDE.md` (global and project): **< 200 lines**, and only what the agent cannot infer. Anything long goes to
  linked docs or skills.
- Skill and subagent descriptions: short; the body loads only on use. Disable skills unrelated to the project
  (`skillOverrides` in `settings.local.json`; the reference project turns off 35 unrelated skills).
- MCP tools: every connected server adds its tools even if you never use them. Defer loading and disable what does
  not apply.
- `SessionStart` hook output: **actionable warnings only**, one line each. `wt:setup` prints nothing when all is
  well.
- Path-scoped rules (`.claude/rules/` with `paths:`): loaded only when working in that area.

Use `/context` to see what is loaded and `/usage` to see what drives spend (per skill, subagent, MCP).

### Entering during the session (variable cost)

- **Symbols before reading:** LSP (definition, references) → Grep by identifier → Read only the range you need. A
  whole file only if you will edit it heavily or it is short.
- **Bounded command output:** `| tail -40`, `| head`, `grep -c`, `--reporter=dot`, `-s`/`--silent`. Full logs go to
  disk (for example `tmp/verify/`) and are read with `tail -n 200` if needed.
- **Tools that summarize:** `verify` prints `✓/✗ step (Ns)` and the last 40 lines of each failure, never the whole
  suite. It is the single largest token optimization in the workflow, and it loses nothing: the log is on disk.
- **Do not re-read what you just wrote:** if the edit did not fail, the file is as you left it.
- **Broad searches go to Explore:** a search subagent returns the conclusion, not the dumps.
- **Independent calls in parallel** within one turn: fewer turns, fewer context resends.

### Context policy thresholds

| Context used | Action |
| --- | --- |
| 0–50% | normal |
| 50–70% | small outputs; symbols before files; delegate broad searches |
| 70–85% | `/checkpoint`; close subtasks before opening new ones |
| ≥ 85% | checkpoint and `/compact <what to keep>` if the task continues; `/clear` + `/checkpoint load` if it changes |

Compaction is a large request (it reads the whole conversation) and loses detail: do it manually, with
instructions, at a natural break. With 1M-token windows the risk is not running out of context; it is **paying** for
useless context on every turn.

## 3. Prompt caching

- The stable prefix (system prompt, `CLAUDE.md`, tools, start of the conversation) is cached. The cache lasts ~1 hour
  on a subscription and ~5 minutes with an API key or a cloud provider; subagents get 5 minutes unless configured
  otherwise.
- **A session left idle beyond the TTL pays for its whole context on return.** If you come back from lunch to a
  200k-token session, `/clear` + `/checkpoint load` is often cheaper.
- Do not change `CLAUDE.md`, skills or MCP servers mid-session unless you must: it invalidates the prefix.
- In your own API integrations: put stable content first (instructions, catalogs, examples) and variable content
  last; mark cache breakpoints; include a **fingerprint** of any compiled content in the cache keys so a change in
  the source invalidates the cache. The reference project does this for its compiled skills: every generation
  cache key carries the fingerprint of the skill files that built the prompt, so editing the catalog never serves a
  draft generated under the old rules, and nobody has to remember to flush anything.

## 4. Effort, model and subagents

| Situation | Effort | Model |
| --- | --- | --- |
| Fast iteration you review step by step, renames, first draft | low | the session's |
| Daily work with clear scope | **medium (default)** | the session's |
| Bug in unfamiliar code, flaky test, schema change with many readers | high | the session's |
| A hard problem with no supervision (security, cross-module design) | max, or `ultrathink` for a single turn | `architect` (opus) |
| Subagent that gathers files, checks links, counts things | — | `haiku` |
| Scoped implementation with a decided plan | — | `builder` (sonnet) |
| Independent review | — | `reviewer` (opus: bug finding is where model quality pays) |
| Root cause of an unclear failure | — | `debugger` (opus) |
| Test strength, docs sync | — | `test-auditor`, `docs-keeper` (sonnet) |

Subagent rules under pressure:

- A subagent **does not give a better answer** (same model, same task); it gives parallelism, noise isolation or
  fresh eyes. If you need none of the three, do it in the main session.
- A complete, narrow brief: goal, what has been ruled out, files to read, format and **length** of the answer
  ("≤ 15 lines", "≤ 700 words").
- Minimal tools in the definition (`tools: Read, Grep, Glob`), enforced by the harness.
- Never delegate 1–2 step tasks: the subagent takes longer to gather context than you take to do them.
- Check `/usage` per subagent type: any that does not earn its cost goes.

## 5. Deterministic work belongs to a script, not the model

The largest lossless saving is not asking the model to do what a program does better:

- **Lint, types and tests through their commands**, never by reasoning about the code ("does it compile?" is a
  question for `tsc`).
- **Debt metrics** via `audit:repo` (seconds, zero tokens); the model only interprets the deltas.
- **Roadmap status** derived from folders, not "remembered".
- **ADR numbering, indexes and generated files** produced by a script inside `land`.
- **Automatic checkpoint** on `PreCompact` without an LLM (branch, commit, diff stat, latest requests).
- **Deterministic fields** of a question card (change, branch, tier) filled in by code.
- In the product: deterministic analysis with the LLM making the decision; deterministic scores in which the LLM
  contributes only the qualitative factors, each with a justification; output checks as code with an id before any
  LLM judge; and when the deterministic analysis leaves nothing actionable, the LLM is not called at all (the run
  closes as "reviewed: nothing to do" at zero cost). Details in §9 and chapter 17.

## 6. Speed: keep the loop short

| Loop | Target | How |
| --- | --- | --- |
| Edit → check | seconds | `verify --quick` (types, structural rules, tests affected via imports); one file with `vitest run <path>` |
| Finish → integrate | minutes | full `verify` inside `land`; slow tests first; half the workers |
| Ask → start | no wait | worktree with dependencies and ports ready at `SessionStart`; nothing to ask inside the accepted scope |
| Blocked → decision | hours, not days | complete question card; assumptions declared instead of waiting |

Practices:

- **A specific opening prompt** (file, symptom, what "fixed" means, preferences): it saves a round of corrections,
  which is the most expensive operation (it re-reads everything).
- **A check that returns pass/fail** from the start: the agent closes the loop on its own and you do not have to
  watch.
- **`Esc` as soon as it drifts**; `/rewind` to try the risky option first.
- **Spec before code** when things are ambiguous: "interview me and write SPEC.md", then a fresh session to build.
- **Do not type "go on" or "don't be lazy"**: give it a check or a `/goal`.

## 7. Parallelism with limits

- **One session per independent task**, each in its own worktree. Several small tasks in parallel finish sooner
  than one session doing them in series with a growing context.
- **Cap concurrent verifications** to the machine (reference project: 3–4 on 36 GB). Above that you get false
  timeouts and burn tokens investigating failures that do not exist.
- **Lands run in series**, never in parallel (the lock enforces it).
- **Dev servers** stopped when you are done looking; orphans reaped automatically.
- **Large mechanical changes** (migrating a hundred files): `/batch` splits them into units, each in its own
  worktree, or loop `claude --bare -p` with `--max-turns` per file. Try three before launching a hundred.

## 8. Unattended runs: hard caps

```bash
claude --bare -p "<task with a definition of done>" \
  --allowedTools "Read,Edit,Bash(pnpm verify *),Bash(git add *),Bash(git commit *)" \
  --permission-mode dontAsk \
  --max-turns 30 \
  --max-budget-usd 3 \
  --output-format json
```

- `--bare` loads no hooks, skills, MCP servers or `CLAUDE.md`: the run behaves the same on any machine and does not
  pay for context it does not use. Pass what it needs explicitly (`--append-system-prompt`, `--settings`).
- Always cap turns and spend; set a spend limit on the account too.
- Protect the integration branch with a rule the run cannot bypass.
- Scheduled reviews (chapter 15) use the same caps.

## 9. Integrating LLMs into your product (for AI developers)

What the reference project does in its own agent runtime, with the decision behind each practice. All of it
carries over to any product built on LLMs. Chapter 17 covers the full architecture (write pipeline, ledgers,
simulator, storage, reversible operations) with its failure modes and enforcement.

- **The SDK in a single module, behind a canonical message format.** The vendor SDK is imported in exactly one
  folder (`llm/`); an architecture test scans core, integrations and apps for the import. The canonical format is
  the main provider's native Messages format (text, tool-use and thinking blocks, stop reason, usage), re-exported
  as local type aliases, **not** a home-made neutral format. Why: a neutral format forces translation in every
  provider, including the only real one, and loses provider features (preserved thinking, effort levels,
  server-side fallbacks, cache control). Another provider family is an *adapter* into the canonical format; cloud
  resellers of the same model use the same format with their own client. Multi-provider SDKs were rejected for the
  same reason plus a heavy dependency.
- **Four modes, one resolution order: `live`, `cache`, `replay`, `mock`.** Integrations and the LLM share them.
  `live` calls the real API and stores the response; `cache` uses the cache within its TTL and goes live
  otherwise; `replay` reads only cache or versioned fixtures and **fails on a miss** (never silently goes live);
  `mock` produces deterministic synthetic data from a seeded RNG. Resolution: explicit flag > environment variable
  > `cache` if credentials exist > `mock`. Every datum carries its `source_mode`, visible in the UI, so synthetic
  data is never mistaken for real data. The LLM side has a real provider, a recording wrapper (`--record` writes
  fixtures), a replay provider keyed by a hash of activity, tenant, model, turn and tool set, and a heuristic mock
  agent that speaks the same protocol. Result: the whole system and its test suite run with no keys and no spend.
- **Budget check before spending, with an estimate.** Before every LLM turn the loop estimates the request cost from
  the prompt size and `max_tokens` and asks the budget guard; before every live integration call the runtime asks
  `canSpend(estimate)` and fails with `budget_exceeded` otherwise. The guard holds a per-run cap and a per-tenant
  monthly cap. Actual cost is recorded after the call and added to the run.
- **Deterministic analysis; the LLM decides only in submit phases.** Every run starts with code that gathers
  evidence and builds a scored backlog. The model then calls only read-only tools and hands in its work through
  three typed tools in a fixed order: `submit_observations` → `submit_decisions` → `submit_plan`. Each is parsed with
  a schema plus business validators (evidence ids exist, opportunities come from the backlog shown, the chosen
  action is allowed, every planned input matches the tool's schema, at most N actions), with **one retry per phase**;
  a second failure fails the run, and a failed run executes nothing (better than executing half a plan). Why: an
  LLM is good at prioritizing and writing, unreliable at calculating, invents data, and must not hold write
  permissions without control. Free-text outputs parsed afterwards and agent frameworks that hide the tool set were
  both rejected.
- **Deterministic scores** ("never: the AI says 73"). The opportunity score is a bounded formula over four factors
  and an effort table; code computes impact and confidence, and the LLM contributes only strategic fit and business
  value, each with a written justification. Same input, same score; the monthly delta is reproducible.
- **Idempotent external effects:** every call that changes the outside world carries an idempotency key and is
  recorded in two phases (`started`, `done`), so a retry or a resumed run never publishes, deploys or buys twice
  (chapter 17).
- **Compiled context with a size budget, per consumer.** Skills that produce text are compiled by a deterministic
  compiler into a different block for each consumer: the planner gets mission and principles; the producer gets
  principles, heuristics, the output contract and 2–3 examples chosen by situation tags; the judge gets the rubric
  and the bad examples. Each consumer has a character budget: required content (principles, contract) is **never
  truncated — if it does not fit, compilation fails**; optional content (heuristics, examples) fills the space left.
  The compiler returns each skill's version and a fingerprint of the block, which goes into the generation cache
  key.
- **Deterministic checks before LLM judges.** Output checks are code with a stable id (platform length limits,
  citable facts only, URLs and phones, promotions, templates, admissions of blame, sensitive data). Rubrics name
  them by id, and an unknown id fails both in the validator and at run time, so a check never passes silently. Each
  numeric limit has a single source that every producer reads. An LLM judge is declared as a rubric method but not
  used until a bench with real cases and a baseline exists to calibrate it.
- **A versioned evaluation bench** run as part of `verify` in mock mode: cases per output type, plus adversarial
  `expect_fail` cases that prove the gate actually bites. A real failure reported by the team becomes a bench case
  through the feedback triage of chapter 15.
- **LLM observability (designed, not yet live in the reference project).** The code speaks only OpenTelemetry; a
  collector decides destinations and filters, so changing vendor is configuration. Operational telemetry carries no
  content and no per-tenant or per-person labels; exactly **one** destination (self-hosted, in-region) receives
  prompts and responses, with emails and phones masked, 90-day retention and audited per-tenant deletion. The
  ledgers remain the source of truth: nothing in the runtime, the budget or customer reports reads from an
  observability tool.

## 10. Measure

Without measurement, "efficient" is a feeling (in a trial with experienced developers, AI tools made them 19%
slower while they believed they were 20% faster). Measure every two weeks, alongside the audit:

| Metric | Source | Why |
| --- | --- | --- |
| Cost per landed change | `/usage` or billing ÷ `landed` lands | output per token, not tokens |
| Land duration p50 and p90 | land log (`<git-common-dir>/<project>-land-log.jsonl`) | speed of the integration loop |
| % of lands with no conflict and no retry | land log | health of parallel work |
| Human interventions per session, by type | session sampling | workflow friction (chapter 12) |
| Churn: code reverted or rewritten within 14 days | `git log` | output that was really cost |
| Failures on the integration branch | CI | the gate works (target: zero) |
| Spend per subagent, skill and MCP server | `/usage` | what earns its cost |

Write down the criterion for rolling back any optimization before you apply it.

## 11. Recommended profile for demanding environments

- `CLAUDE.md` < 200 lines; path-scoped rules; unrelated skills disabled; minimal MCP servers.
- `verify` with summary + tail and two levels; `land` serialized with a lock.
- Medium effort by default; high per task; `architect` only for hard problems; `haiku` for mechanical subagents.
- One task, one session, one worktree; `/clear` between tasks; checkpoint at 70%.
- Cap of 3–4 concurrent verifications per 32–36 GB machine (tune it by measuring).
- Unattended runs always with `--bare`, `--max-turns`, `--max-budget-usd`.
- Scheduled read-only reviews with caps.
- The §10 metrics in every audit.

## What not to do to save tokens

- Lossy compression of diffs or logs so they "fit".
- Skipping full verification because the quick one passed.
- Lowering effort on tasks where a mistake is expensive.
- Dropping independent review on sensitive paths.
- Keeping one endless session "so as not to lose context": old context is paid for on every turn and makes the
  answers worse.
